# 5.227.11: the first message to the assistant after a pause answers sooner

## What a person saw

After a quiet spell, the first message to the assistant took about 9 seconds; the next ones took about 3 seconds.

## Measured before

Production, 15 Nov 2026 18:38, first chat request on a new deployment: 9.1 s, then 3.6 s and 3.3 s. The log line added in 5.227.10 read `[rate-limit] first store call of this instance took 2019 ms` (function region sin1). The limiter's store was reached only when the gate had already finished, so the 2 s handshake sat in line with everything else.

## The change

- `api/_lib/rate-limit.js`: `warmStore()` sends one `PING` through the existing pipeline function, not awaited, errors swallowed, at most one in flight, nothing once the store has answered or when it is not configured. It never counts against a limit and never fails a request.
- `api/ai-chat.js` and `api/ai-voice.js`: a POST calls `warmStore()` at the top of the handler, so the handshake runs while the gate answers.
- `api/_lib/ai/limits.js` (`checkLimits`): read in full. The burst and day windows already go out together. The shared daily budget depends on both (it must not be drained by a request a window refused, and the day count is refunded when the burst refuses), so that one stays after them. No refusal, refund or message changed; only a comment says why.

## Checks

- `tests/unit/rate-limit-warm.test.mjs`: the warm call is one `PING` per instance and one in flight; a failing warm call changes nothing; it never counts against a limit.
- `tests/unit/rate-limit-cold-start.test.mjs`, `api-limits.test.mjs` and the other limiter tests pass unchanged.

## Not yet measured

The time after the change can only be read on production: the log line `first store call of this instance took N ms` (the warm call logs it now, before the request needs the store) and one timed first chat request after a deployment. Neither has been read yet.
