# 5.185.0: opening library documents

Palm, 1 Nov 2026: "ระบบเปิดเอกสารเราทำได้เสถียรกว่านี้นะครับ ตอนนี้มันยังดูบัคๆ บัคเยอะอยู่มาก". Every way a student
opens a library document was walked on vetmock.com (5.177.0) in six Playwright profiles (Chromium desktop, Pixel 7,
iPhone 13 and iPad Pro WebKit, Firefox, and a LINE user agent on WebKit), with the catalog checked against R2 and
the document routes probed with curl. Each bug below has a regression test that fails on origin/main 7d9890f2.

## Bugs, causes, fixes

1. **Reload, browser Forward, or iOS reloading a tab it killed lost the deck.** Every engine landed on the empty
   "เปิด PDF แล้วเขียนทับได้เลย" page at `/app/tools/pdf`. Cause: the shelf deck lived only in App state
   (`libraryDoc`), never in the address. Fix: the reader's address names the deck, `/app/tools/pdf?doc=<slug>`
   (`readerUrl`/`readerTarget` in `view-route.js`); App reopens it from the address on boot and on Forward, and the
   reader finds the row itself (`findLibraryDoc`: the device's shelf snapshot, then one catalog row, then the merged
   catalog with the VCA cards). A link may add `&page=N`; it is honoured once and dropped, so a later reload resumes
   at the last page read. A signed-in owner change still closes the deck and now clears the address too.
   Proof: e2e "a shelf deck reopens after a reload, and after Back then Forward" and "a link opens a deck at the page
   it names"; unit "a deck named only by the reader address opens from its row".
2. **A loading or failed deck showed under the personal-file dropzone.** On an iPhone 13 the screen read "เปิด PDF
   แล้วเขียนทับได้เลย" and "เลือกไฟล์ PDF", with "กำลังเปิดเอกสาร…" and the retry button under the bottom bar; no
   title, no other way to the file. Fix: a shelf deck gets its own panel: title at the top, progress, and on failure
   the reason with ลองเปิดอีกครั้ง, เปิดไฟล์ต้นฉบับ and ดาวน์โหลดไฟล์; in LINE, เปิดในเบราว์เซอร์ on the same deck
   (`openExternalBrowser=1`), in other app browsers the menu hint, and no download button (app browsers do not save
   files, as VetMock AI already decided). A deck the address names but the shelf no longer has says so, and says
   when it needs a sign-in instead (a guest's shelf holds public rows only; an anonymous mint answers 401); a
   non-PDF named there is offered as a file. Proof: e2e "a deck that cannot open says why at the top of a phone" (the
   retry is tappable, nothing on top of it) and "inside LINE"; unit "a deck the reader address names but a guest's
   shelf lacks says whether it needs a sign-in".
3. **Safari before 17.4 could open no PDF.** pdf.js 4.10's modern build calls `Promise.withResolvers` (Safari 17.4,
   March 2024), far above the iOS 14 floor that `platform-compat.test` keeps for the app; every deck failed with a
   retry that could never work (reproduced on vetmock.com by removing the API in WebKit: "Promise.withResolvers is
   not a function"). Fix: `loadPdfjs` loads pdf.js's legacy build and its worker where the API is missing, in a chunk
   of its own (`vendor-pdf-read-legacy`), so current browsers never fetch it. pdf.js ships that worker as ES2022 (a
   class static block, Safari 16.4), so it is built through Vite's worker pipeline (`?worker&url`): the built worker
   and chunk parse as ES2020 (checked with acorn). Proof: e2e "a browser without Promise.withResolvers still opens a
   PDF" and unit "a browser without Promise.withResolvers gets the legacy pdf.js build and its worker" (simulated in
   current engines; no device on iOS 14 to 17.3 was tested, and runtime APIs below Safari 16.4 are unproven).
4. **214 Word, PowerPoint and Excel files went out as `application/octet-stream` attachments.** "openxmlformats" in
   their type matched the html/xml guard in `/api/library-blob` `contentHeaders`, and the same regex in the worker's
   `labelled()`. Fix: the three Office Open XML types are exempt by exact match and go out as themselves, inline;
   anything a browser renders as a page stays a download. Proof: unit "Word, PowerPoint and Excel files go out as
   themselves" and "a Word file kept for offline opens as itself"; production before the fix, a .docx answered
   `Content-Type: application/octet-stream`, `Content-Disposition: attachment`.
5. **Library videos answered a byte range with the whole file.** The Cloudflare object API ignores Range (rechecked
   1 Nov: `bytes=0-1023` returned 807,940 bytes, 200), so `/api/library-blob` sent 200 and `Accept-Ranges: none`, and
   the worker answered ranges from its whole copy; Apple's media guidance requires 206 answers on iPhone and iPad.
   Fix: for `video/*` and `audio/*` only, the function cuts the asked range from the stream (`sliceBody`, reusing the
   archive worker's `byteRange`), measured against the object's own length rather than the catalog's, and answers
   206 with `Content-Range`; 416 when the range is outside the file. The worker answers a range from its kept copy
   with 206 (offline too, so a cached clip still plays in Chrome and Firefox), sends a range it has no copy for to
   the network as asked, and keeps a whole-file 206 (a player's first `bytes=0-`) as the file. PDFs stay whole: a
   viewer told it may seek would pull the deck once per range. Proof: unit "a video answers a byte range with
   exactly those bytes and 206", "the object, not the catalogue, measures a range", "a range lets storage go", "a
   video's byte-range reads get 206", "a clip whose first read is a whole-file 206 is still kept for offline".
   Playback on a real iPhone or iPad was not tested.
6. **Every guest launch re-read, re-hashed and rewrote the offline document cache, twice.** Measured on vetmock.com
   with two cached decks: two deletions of `vmx-lib-docs-v1` and 3,253,430 bytes hashed per launch; a phone that
   kept six decks of up to 40 MB paid that on every boot. Cause: `setLibraryAccess(false)` purged on every signed-out
   report, and a boot reports twice. Fix: a signed-out device purges until one purge has finished (`purged` on the
   access record, set only on the record that call wrote), then a guest who stays a guest pays nothing; the worker
   never stores a restricted deck without a live session. Proof: unit "a guest who stays a guest does not re-read,
   re-hash and rewrite the offline shelf on every launch" and "a sign-out purge cut short runs again at the next
   launch" (the security review found the first version of this fix skipped that retry).
7. **A failed open over an open deck said nothing.** The viewing screen has no place for an error, so a command
   palette deck that failed left the old deck up and silent. Fix: a new deck clears the screen into its opening panel
   (after flushing the ink of the one on screen). When App takes the deck away (a sign-out in another tab remounts
   the reader still holding it for a render), the open still in flight is withdrawn instead of being shown to whoever
   is there now. The row lookup is bounded (8 s) and pdf.js loads beside it.

8. **A text match inside a grouped VCA file never showed.** A VCA card groups several files under the slug of one;
   the shelf joined text-search rows to card slugs only, so a match inside any other copy (146 of the 440) was
   dropped: 1 of the 8 archive matches for "diagnosis" on 1 Nov. Fix: `contentHitRows` joins a match to the card's
   own PDF copies too, opened by range like the card. Proof: unit "a text match inside any PDF a VCA card groups is
   shown and opens that file".

Also: "เปิดไฟล์ต้นฉบับ" (shelf, palette, reader) shares `openDocInTab`; when the browser gives no tab it opens the
file in place instead of asking for a tab again after the mint, which browsers refuse without a word (unit "a file
opens in the tab opened inside the tap, or here when the browser gives no tab"). The reader's ดาวน์โหลดไฟล์ names
the file on the blob route and, offline, says when the device has no copy instead of saving the 503 as the file; a
VCA archive copy, read by range from the archive worker's origin, has no download button (its own tab saves it).

## Reviews

Two independent reviews of the diff. The security and data-integrity review found one regression in this branch's
first version (a sign-out purge cut short was never retried, item 6, fixed and tested) and asked for the range to
be measured by the object (item 5, fixed), for whole-file 206 answers to be kept offline (fixed) and for the
download button not to navigate the app to an archive copy (fixed). It checked and found safe: the Office exemption
(exact, anchored match; `+html` and charset variants still go out as attachments), the 206 headers (token and
expiry checked first, integers only), the worker's range answers (same access checks as a whole read; a signed-out
device gets 503 for every range), the deep link (public snapshot, then one row under RLS) and the LINE link (no
token in it). Accepted, with their limits stated:
- A range is cut from a whole-object read, so a seek near the end of a large video reads the whole object through
  the function, and every media range counts against the per-link budget (300 per 10 minutes per address); a class
  of iPhones behind one address playing one clip can reach it. The upgrade path is serving media through the
  archive worker's R2 binding, which reads ranges natively.
- The reader's address names the deck, so a deck's slug stays in the browser's history on a shared device, as the
  shelf's search terms already do; every deck is public today.
- When the browser gives no tab, the file opens in the app's own tab, so its signed link (valid up to 75 minutes)
  sits in that tab's history.

The general review found two definite bugs, both fixed and tested: a login-only deck named by the address read as
"removed" for a guest (item 2), and the legacy worker could not parse below Safari 16.4 (item 3); it also asked for
the in-flight open to be withdrawn on a sign-out (item 7). It confirmed no loop between the restore, leave-reader and
owner-change effects. Also from it: on Chromium a deck chosen in the search palette from Home is dropped by App for a
render while the view transition runs, and the reader's address now reopens it (before this release that path most
likely opened an empty reader); e2e "a deck chosen in the search palette on Home reaches the reader". Accepted:
- The address keeps only the slug, so a palette open from a non-origin screen carries no page; no palette entry
  carries one today.
- `findLibraryDoc` answers from the device's shelf snapshot first, refreshed whenever the shelf, the palette or a
  related-documents list loads the catalog; slugs carry a hash prefix, so new bytes get a new slug.
- A sign-out rewrites the reader's address on the current history entry only; Back can reopen an earlier entry's
  public deck, as any page in the browser's history can.
- VCA Word and Excel copies come from the archive worker, which still sends them as attachments; changing that needs
  a worker deploy.
- `downloadDocFile` opens any link that is not the blob route (none on the shelf today besides the one Supabase-hosted
  deck) in the app's tab; both caches answer a multi-range or malformed `Range` with 416 (no browser sends one).

## Checked, not changed

- R2 against the catalog: 2,147 rows, 0 missing objects, 0 size mismatches. Data notes for the vet-86 lane: one
  `.doc`, one `.txt` and one `.xlsm` row carry `application/octet-stream`.
- An 18 MB deck through `/api/library-blob` at a throttled 50 KB/s took 357 s and arrived whole (sha verified): no
  function time cap was hit at that length.
- Offline reopen from the worker cache works on Chromium, Firefox and Android emulation; WebKit failed only under
  Playwright's offline emulation (the worker answers 200 from the cache when asked online).
- The in-app page jump from a content hit works in every engine (หน้า 8 / 22).

## Not in this release

- VetMock AI "เปิด" and "เปิดหน้า N" open `/api/library-file?...&open=1#page=N`, and only desktop Chrome and Firefox
  honour `#page`: iPhone and iPad open page 1, Android often downloads. The fix is `fileLinks().open` pointing at the
  reader address added here; it touches the hunk PR #129 (Chula sign-in) changes, so it follows #129, as that lane
  asked.
- The document routes ran in iad1 when this was measured (mint 1.2 to 1.8 s from Bangkok); 5.180.0 (#130, perf
  lane) moved them to sin1.

## With the Chula sign-in wall (5.184.0)

#129 merged first, so, as agreed with that lane, this release adds the guard: the restore effect waits for
`wall.state === 'open'` (the gate renders over any `/app` path without navigating, so the reader's address survives
sign-in, and a guest's mint would only be refused). `resolveDocUrl` mints anonymously first and retries with the
member's bearer on the gate's 401, which is what the wall's API answers a request with no or a refused token.
