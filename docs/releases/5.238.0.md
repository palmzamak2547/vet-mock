# 5.238.0: เปิดเอกสารจากคลังแล้วเห็นหน้าแรกได้เร็วขึ้นมาก ไม่ต้องรอโหลดทั้งไฟล์

## เจออะไร

15 พ.ย. 2569 เวลา 21:46 เปิดเอกสาร 24.5 MB จากคลังเอกสารบนมือถือผ่าน 5G แล้วเห็น "กำลังโหลด 1.3 / 24.5 MB" ค้างที่ 5%
หน้าอ่าน PDF โหลดไฟล์ครบทุกไบต์ก่อนจึงวาดหน้าแรกได้ เพราะ PDF เก็บสารบัญของไฟล์ (cross-reference table) ไว้ท้ายไฟล์
และในคลังมีเอกสารที่จัดให้อ่านจากต้นไฟล์ได้ (linearized) อยู่ไฟล์เดียว

## วัดก่อนแก้

วัดบน build ในเครื่อง กับ endpoint จำลองที่ส่งไฟล์จริงสามไฟล์ (2.2, 10.7, 24.4 MB) ทุก response ผ่านลิงก์จำลองเส้นเดียว
ค่ากลางจาก 3 รอบ ตารางเต็มและวิธีวัดอยู่ที่ `work/doc-open-speed/BEFORE.md` และ `AFTER.md` (ในเครื่อง ไม่ commit)

| ไฟล์ 24.4 MB | หน้าแรกขึ้น | ไบต์ที่มาถึงก่อนหน้าแรก | ทุกหน้าพร้อม |
|---|---|---|---|
| ก่อนแก้ 10 Mbit/s, 40 ms | 21.3 s | 24.4 MB | 21.3 s |
| หลังแก้ 10 Mbit/s, 40 ms | 3.2 s | 3.4 MB | 21.9 s |
| หลังแก้ อ่าน range ตรงจากที่เก็บ (วัดซ้ำหลังแก้ตามรีวิว) | 3.2 s | 3.5 MB | 21.9 s |
| ทาง REST สำรอง ถ้าที่เก็บอ่านได้ 25 MB/s (สมมติ) | 7.0 s | 7.9 MB | 21.9 s |
| ก่อนแก้ ไม่จำกัดความเร็ว | 0.6 s | 24.4 MB | 0.6 s |
| หลังแก้ ไม่จำกัดความเร็ว | 0.6 s | 25.1 MB | 0.6 s |

ไฟล์ 2.2 MB: 2.5 s เป็น 2.1 s ไฟล์ 10.7 MB: 9.7 s เป็น 8.6 s (pdf.js ต้องการ 56 ช่วงกระจายทั้งไฟล์ ช่วงที่ขอได้ 6 ช่วงครอบคลุมไม่หมด)
ตัวเลขเป็นของเน็ตทดสอบ ไม่ใช่สัญญาว่ามือถือทุกเครื่องจะได้เท่านี้

## แก้อย่างไร

- เริ่มโหลดไฟล์ทันทีที่ได้ลิงก์ ไม่รอโค้ดของ pdf.js โหลดเสร็จก่อน และเรียก `getDocument` ทันทีที่รู้ขนาดไฟล์ worker ของ pdf.js จึงโหลดไปพร้อมไฟล์
- ไฟล์ทั้งก้อนยังโหลดเหมือนเดิม แต่ส่งให้ pdf.js ทีละส่วนที่มาถึง ส่วนที่ pdf.js ต้องใช้แต่ยังไม่มาถึง (ท้ายไฟล์ และวัตถุของหน้าแรก)
  ขอแยกด้วย byte range (`src/lib/pdf-range-source.js`): ท้ายไฟล์ 3% (512 KB ถึง 2 MB) ขอตั้งแต่ต้น ช่วงอื่นทีละ 128 KB
  ไม่เกิน 6 ช่วงต่อการเปิดหนึ่งครั้ง ไม่ขอเพิ่มหลังวาดหน้าแรกแล้ว และไฟล์เกิน 40 MB ขอได้ไม่เกินสามเท่าของขนาดไฟล์ตามที่เซิร์ฟเวอร์นับ
- หน้าอื่น รูปย่อหน้า การค้นในเอกสาร และการส่งออก รอไฟล์ทั้งก้อนที่กำลังมา การส่งออกไม่เริ่มโหลดซ้ำอีกรอบ
  ถ้ากดค้นตอนไฟล์ยังมาไม่ครบ จะขึ้นว่าไฟล์ยังโหลดไม่ครบ
- service worker ยังเก็บไฟล์ทั้งก้อน (40 MB ลงมา หกไฟล์) เหมือนเดิม เปิดครั้งที่สองในเครื่องเดิมจึงไม่โหลดใหม่ และเปิดออฟไลน์ได้เหมือนเดิม
  สำเนาที่เก็บไว้อ่านแบบทั้งก้อนเสมอ
- ใช้ทางเดิมทั้งหมด (โหลดทั้งก้อนแล้วจึงเปิด) เมื่อ: เซิร์ฟเวอร์ไม่ตอบ `Accept-Ranges: bytes` ไม่มีความยาว มีการบีบอัด
  เป็นสำเนาจาก service worker หรือคำตอบของ range ไม่ใช่ 206 ที่มี Content-Range ตรงกับที่ขอ (ปิด range แล้วรอไฟล์ทั้งก้อน)
  ถ้าการโหลดทั้งก้อนขาดกลางทาง จะขอต่อจากจุดที่ขาดครั้งเดียว ด้วย range เดียวไปจนจบไฟล์ เพดานจำนวน range ยังเท่าเดิม
  ถ้าขอต่อไม่ได้ จะไม่ขออะไรเพิ่มอีก ก่อนหน้าแรกจะขึ้นข้อผิดพลาด หลังหน้าแรกจะบอกให้เปิดใหม่
- เอกสาร linearized และสำเนา VCA ยังเปิดผ่าน URL แบบเดิม
- เซิร์ฟเวอร์อ่านไฟล์จากที่เก็บด้วยคำขอแบบ S3 ที่ลงชื่อในฟังก์ชัน ซึ่งอ่านเฉพาะช่วงที่ขอได้ จึงนับแต่ละช่วงตามไบต์ที่ส่งจริง (รายละเอียดในหัวข้อถัดไป)

ไฟล์: `src/lib/pdf-range-source.js` (ใหม่), `src/views/PdfAnnotateView.jsx` (`ingestRemote`, `cachePage`, แถบค้นหา),
`src/lib/pdf-export.js` (`readSourceBytes` รอ `ready`), `api/library-blob.js`

ต่อจาก 5.237.0 (หน้าโหลดไม่ทับกัน) ซึ่ง merge เข้ามาในสาขานี้แล้ว ไม่ได้แตะ markup หรือ CSS ของหน้าโหลด

## What a member could do before and after

The change is in `api/library-blob.js`, the endpoint that streams a library object from private R2 behind a
signed, expiring link minted by `api/library-file.js`.

Before:
- A member with a valid link for a document could GET it whole, as often as the limits allowed: 300 requests per
  link per 10 minutes, and 2 GB per member per 10 minutes, each GET counted at the document's catalogued size.
  Storage was read through the Cloudflare REST API, which ignores Range; a Range header on a document got the
  whole object with `Accept-Ranges: none`. Video and audio were cut to ranges (206) here and are outside the
  byte budget.

After:
- Storage is read through R2's S3 API with a request this function signs (`presign()` in `api/_lib/r2.js`, with
  `tokenKeyEnv()` turning the standing `CLOUDFLARE_API_TOKEN` into its S3 key pair, as `api/video-file.js` already
  does for videos). The signed URL lives 120 s, is made per request on the server, never leaves it, and the
  account token is not sent to storage. R2 honours Range there, so a range reads only its own bytes. The whole
  file is read the same way (one route, and media seeks no longer read from byte 0). No new environment variable:
  the route uses `CLOUDFLARE_API_TOKEN` and `R2_ACCOUNT_ID`, which the endpoint already required.
- When the S3 route cannot be signed or is refused (a token without that ability, a 403 or a storage fault), the
  endpoint falls back to the REST API as before; there a range is cut from the whole object and counted from
  byte 0, and a range first counted as its own bytes has the prefix counted before it is read. A failed route is
  not retried for five minutes.
- The member may ask for a byte range of a document whose size is catalogued (the size is in the signed token).
  It is answered 206 with `Accept-Ranges: bytes` and counted before serving as the bytes storage sends for it:
  the range's own length through S3, every byte up to its end through REST, never more than the object.
- A malformed or multiple Range on a document is ignored and the whole file answered with 200 (RFC 9110), instead
  of a 416 after the whole file had been counted.
- Who may read is unchanged: the signature check on the link runs first on every request, ranges included (a
  forged or altered token is 403 and reaches no storage, tested); `library-file.js` is not changed, so the Chula
  wall, the RPC that decides who sees a storage key, open tickets and the hold that signs a personal-data
  document as restricted are where they were. A restricted range is `Cache-Control: no-store` like the whole
  file, and the service worker never keeps a partial answer.
- Limits are not loosened: 300 requests per link and 2 GB per member per 10 minutes, the same numbers. Looping
  the 64 KB tail of a 100 MB deck is refused at the 301st request on the link (storage has then sent about
  19 MB); looping the whole deck by range (`bytes=0-`) is refused after 20, exactly as twenty whole opens were;
  on the REST fallback looping the tail is refused after 20 as well. All three are tested.
- The reader (`src/lib/pdf-range-source.js`): at most 6 ranges per open, none after page one is drawn, at most 3x
  a file over 40 MB. A download that drops is picked up once with one range from where it stopped to the end
  (counted as those bytes); the limits stay in force, and if the pick-up fails nothing more is fetched. Before
  this fix a drop removed the limits and every page turn became a range (review of #283; tested now).
- What an honest open costs now (S3 route, as measured on the 24.4 MB deck: the file, its 748 KB tail and five
  128 KB reads): 25.7 MB, so 79 opens of a 24 MB deck fit in ten minutes (80 before ranges, when an open cost
  the file). A 100 MB deck of the same shape: 102.6 MB, 19 opens (20 before). A reopen of a file of 40 MB or less
  comes from the device and costs nothing. On the REST fallback: 136 MB, 15 opens of the 24 MB deck, and at most
  400 MB, 5 opens of a 100 MB deck. Pinned in `tests/unit/library-blob-ranges.test.mjs`.

Tests: `tests/unit/library-blob-ranges.test.mjs` (the signed ranged read and what it sends, the fallback and its
count, malformed ranges, both counts, the three abuse cases, the budgets, the signature on a range, no-store on a
restricted range, unsized stays whole). The REST-route tests in `api-limits`, `api-hardening`,
`library-blob-stream`, `library-blob-settle`, `library-cache-security` and `library-doc-open` turn the S3 route
off (`setDirectStorage(false)`) and still pass; four assertions there that pinned `Accept-Ranges: none` or a 200
for a document range pin the new answer.

## การทดสอบ

- `tests/unit/pdf-export-source.test.mjs`: การส่งออกรอไฟล์ที่กำลังมาแทนการโหลดซ้ำ
- `tests/e2e/library-doc-speed.spec.js`: เซิร์ฟเวอร์ส่ง 1 MB แรกของไฟล์ 8 MB แล้วชะลอ หน้าแรกต้องขึ้นตอนที่ไฟล์มาไม่ถึง 20%

  ผ่านบน chromium desktop, chromium mobile และ firefox ในเครื่อง
- ที่รันแล้วผ่าน: unit ของหน้าอ่าน PDF (`pdf-reader-*`, `pdf-live-sync-loop`, `pdf-annotations`, `pdf-text-cache`, `pdf-export-source`)

  บน chromium; `lint:voice` และ `lint:motion` ไม่เพิ่ม, `perf:budget` ผ่านโดยไม่ขยับงบ

## ยังไม่ได้ตรวจ

- production: ต้องใช้บัญชีจุฬาที่เข้าสู่ระบบ จึงวัดจากที่นี่ไม่ได้ ยังไม่ได้ลองว่า token ที่ใช้อยู่ลงชื่อคำขอ S3 ของคลังเอกสารได้จริง
  (ทางเดียวกับวิดีโอซึ่งใช้งานอยู่) ถ้าไม่ได้ จะกลับไปใช้ทาง REST และนับแบบเดิมเอง เวลาที่ฟังก์ชันใน sin1 ใช้รอไบต์แรกจาก R2 ยังไม่รู้
  และการเปิดครั้งแรกของแต่ละ instance ต้องถาม Cloudflare หา key id ของ token หนึ่งครั้ง (เก็บไว้ 6 ชั่วโมง)
- WebKit: ในเครื่อง Windows ทั้ง spec ใหม่และ `library-doc-loading-layout` ของ 5.237.0 ไม่ผ่าน เพราะ WebKit บน Windows
  ไม่ส่ง body ที่ยังมาไม่ครบให้หน้าเว็บ ปล่อยให้ CI (Linux) ตรวจ
- มือถือจริง และไฟล์ 100 MB จริง

## ต่อไป

- ไฟล์ที่ต้องการวัตถุกระจายทั้งไฟล์ (แบบไฟล์ 10.7 MB) จะเร็วขึ้นได้ถ้าให้ขอ range ได้มากกว่า 6 ช่วง ตอนนี้แต่ละช่วงนับตามไบต์จริงแล้ว
  เพดานนี้จึงผ่อนได้ ต้องวัดก่อน
- ดึงรอยเขียนของบัญชี (`pullAndMerge`) ไปพร้อมกับเปิดไฟล์ แทนที่จะรอหลังเปิด ยังไม่ได้วัด จึงยังไม่ทำ
