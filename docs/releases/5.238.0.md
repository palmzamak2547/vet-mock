# 5.238.0: เปิดเอกสารจากคลังแล้วเห็นหน้าแรกได้เร็วขึ้นมาก ไม่ต้องรอโหลดทั้งไฟล์

## เจออะไร

15 พ.ย. 2569 เวลา 21:46 เปิดเอกสาร 24.5 MB จากคลังเอกสารบนมือถือผ่าน 5G แล้วเห็น "กำลังโหลด 1.3 / 24.5 MB" ค้างที่ 5%
หน้าอ่าน PDF โหลดไฟล์ครบทุกไบต์ก่อนจึงวาดหน้าแรกได้ เพราะ PDF เก็บสารบัญของไฟล์ (cross-reference table) ไว้ท้ายไฟล์
และในคลังมีเอกสารที่จัดให้อ่านจากต้นไฟล์ได้ (linearized) อยู่ไฟล์เดียว

## แก้อย่างไร

- เริ่มโหลดไฟล์ทันทีที่ได้ลิงก์ ไม่รอโค้ดของ pdf.js โหลดเสร็จก่อน และเรียก `getDocument` ทันทีที่รู้ขนาดไฟล์ worker ของ pdf.js จึงโหลดไปพร้อมไฟล์
- ไฟล์ทั้งก้อนยังโหลดเหมือนเดิม แต่ส่งให้ pdf.js ทีละส่วนที่มาถึง ส่วนที่ pdf.js ต้องใช้แต่ยังไม่มาถึง (ท้ายไฟล์ และวัตถุของหน้าแรก)
  ขอแยกด้วย byte range (`src/lib/pdf-range-source.js`): ท้ายไฟล์ 3% (512 KB ถึง 2 MB) ขอตั้งแต่ต้น ช่วงอื่นทีละ 128 KB
  ไม่เกิน 6 ช่วงต่อการเปิดหนึ่งครั้ง ไม่ขอเพิ่มหลังวาดหน้าแรกแล้ว และไฟล์เกิน 40 MB ขอได้ไม่เกินสามเท่าของขนาดไฟล์ตามที่เซิร์ฟเวอร์นับ
- หน้าอื่น รูปย่อหน้า การค้นในเอกสาร และการส่งออก รอไฟล์ทั้งก้อนที่กำลังมา การส่งออกไม่เริ่มโหลดซ้ำอีกรอบ
  ถ้ากดค้นตอนไฟล์ยังมาไม่ครบ จะขึ้นว่าไฟล์ยังโหลดไม่ครบ
- service worker ยังเก็บไฟล์ทั้งก้อน (40 MB ลงมา หกไฟล์) เหมือนเดิม เปิดครั้งที่สองในเครื่องเดิมจึงไม่โหลดใหม่ และเปิดออฟไลน์ได้เหมือนเดิม
  สำเนาที่เก็บไว้อ่านแบบทั้งก้อนเสมอ
- ใช้ทางเดิมทั้งหมด (โหลดทั้งก้อนแล้วจึงเปิด) เมื่อ: เซิร์ฟเวอร์ไม่ตอบ `Accept-Ranges: bytes` ไม่มีความยาว มีการบีบอัด
  เป็นสำเนาจาก service worker หรือคำตอบของ range ไม่ใช่ 206 ที่มี Content-Range ตรงกับที่ขอ (ปิด range แล้วรอไฟล์ทั้งก้อน)
  ถ้าการโหลดทั้งก้อนขาดกลางทาง ส่วนที่เหลือขอด้วย range ต่อ ถ้าทำไม่ได้ก่อนหน้าแรกจะขึ้นข้อผิดพลาด หลังหน้าแรกจะบอกให้เปิดใหม่
- เอกสาร linearized และสำเนา VCA ยังเปิดผ่าน URL แบบเดิม

ไฟล์: `src/lib/pdf-range-source.js` (ใหม่), `src/views/PdfAnnotateView.jsx` (`ingestRemote`, `cachePage`, แถบค้นหา),
`src/lib/pdf-export.js` (`readSourceBytes` รอ `ready`), `api/library-blob.js`

## What a member could do before and after

The change is in `api/library-blob.js`, the endpoint that streams a library object from private R2 behind a
signed, expiring link minted by `api/library-file.js`.

Before:
- A member with a valid link for a document could GET it whole, as often as the limits allowed: 300 requests per
  link per 10 minutes, and 2 GB per member per 10 minutes, each GET counted at the document's catalogued size.
  A Range header on a document was forwarded to storage, which ignores it, and the whole object was returned
  with `Accept-Ranges: none`. Video and audio were cut to ranges (206) and are outside the byte budget.

After:
- The same member, with the same link, may also ask for a byte range of a document whose size is catalogued
  (the size is in the signed token, so a member cannot change it). The endpoint cuts the range from the whole
  object storage sends, answers 206 with `Accept-Ranges: bytes`, and counts it before serving as every byte from
  the start of the object to the end of the range (`bytesPulled(payload, media, range)`, at most the object's
  size). That is what the function really reads from storage, so a range is never cheaper for the member than it
  is for the server.
- Who may read is unchanged: the signature check runs on every request, ranges included (a forged or altered
  token is 403, tested); `library-file.js` is not changed, so the Chula wall, the RPC that decides who sees a
  storage key, and the hold that signs a document with personal data as restricted are untouched. A restricted
  range is `Cache-Control: no-store` like the whole file, and the service worker never keeps a partial answer.
- Limits are not loosened: the 300 requests per link and the 2 GB per member are the same numbers. The abuse a
  range could open, asking for the tail of a big file over and over to make the function read it whole for a
  64 KB answer, is counted at the whole file each time: looping the tail of a 100 MB deck is refused after 20
  requests, exactly where looping the whole deck was (tested). Cheap ranges near the start are still capped at
  300 per link (tested).
- A document of unknown size is unchanged: whole, `Accept-Ranges: none`, counted as it streams.
- No credential moved: the range requests use the same signed link (`t`, `s` in the query, as before); no new
  header, cookie or token, and nothing new is logged.
- What it costs an honest member: the measured open of a 24.4 MB deck counts about 136 MB (the file plus six
  ranges), so 15 such opens fit in ten minutes instead of 80; a reopen of a file of 40 MB or less comes from the
  device and costs nothing. A file over 40 MB spends at most three times its size on ranges, so a 100 MB file
  costs at most 400 MB per open: 5 opens in ten minutes instead of 20.

Tests: `tests/unit/library-blob-ranges.test.mjs` (the cut, the count, both abuse cases, the budget for 25 MB and
100 MB, the signature on a range, no-store on a restricted range, unsized stays whole); two assertions in
`api-limits.test.mjs`, `library-blob-stream.test.mjs` and `library-doc-open.test.mjs` that pinned
`Accept-Ranges: none` or a 200 for a document range now pin the new answer.

## ยังไม่ได้ตรวจ

- production: ต้องใช้บัญชีจุฬาที่เข้าสู่ระบบ จึงวัดจากที่นี่ไม่ได้ endpoint จำลองไม่ได้จำลองฟังก์ชันใน sin1 ที่อ่านไฟล์จาก R2
  ทุก range ต้องอ่านตั้งแต่ไบต์แรก ความเร็วจริงตรงนี้ยังไม่รู้ (แถว 25 MB/s ในตารางเป็นค่าสมมติ)
- WebKit: ในเครื่อง Windows ทั้ง spec ใหม่และ `library-doc-loading-layout` ของ 5.237.0 ไม่ผ่าน เพราะ WebKit บน Windows
  ไม่ส่ง body ที่ยังมาไม่ครบให้หน้าเว็บ ปล่อยให้ CI (Linux) ตรวจ
- มือถือจริง และไฟล์ 100 MB จริง

## ต่อไป

- ไฟล์ที่ต้องการวัตถุกระจายทั้งไฟล์ (แบบไฟล์ 10.7 MB) จะเร็วขึ้นได้ด้วยการขอหลายช่วงในคำขอเดียว (อ่านที่เก็บครั้งเดียว ตอบ multipart)
  หรือการอ่านที่เก็บแบบเริ่มกลางไฟล์ได้ (R2 binding แบบ archive worker) ซึ่งจะทำให้ range ไม่ต้องนับเต็มไฟล์ด้วย
- ดึงรอยเขียนของบัญชี (`pullAndMerge`) ไปพร้อมกับเปิดไฟล์ แทนที่จะรอหลังเปิด ยังไม่ได้วัด จึงยังไม่ทำ
