# 5.178.0: every visitor signs in with a Chula Google account

VetMock (vetmock.com, ai, vca and research) is for Chula students and staff: a visitor signs in with a Google
account on `@student.chula.ac.th` or `@chula.ac.th` before using it. The database decides; the front ends only
explain. Design, layers and limits: [../CHULA-SIGNIN.md](../CHULA-SIGNIN.md). The wall ships off and is switched
on once this release is live.

- **Database** (`supabase/migrations/20261101170000_chula_wall.sql`): one switch, `private.chula_wall.enforce`
  (a missing row reads as on). A member holds a Google identity whose email Google verified, on a Chula domain,
  with Google's hosted-domain claim naming it; the admin also passes. Layers: the before-user-created Auth hook
  and a trigger on `auth.users` (a Chula address arrives only through Google, wall on or off), a trigger on
  `auth.identities` (no unverified OAuth identity joins an existing account), PostgREST's pre-request (covers
  SECURITY DEFINER RPCs; four calls allow-listed), and a restrictive policy on every table in `public` and `vca`,
  `storage.objects` and `realtime.messages`.
- **API**: every `api/*.js` that costs money or touches an account checks the caller (`api/_lib/chula-gate.js`);
  the rest are listed as open with their reason, and a test fails on a file in neither list. Library links a
  student taps carry a ticket for one document for a day (`api/_lib/open-ticket.js`).
- **vetmock.com**: the sign-in screen (Google's own button and One Tap, never the supabase.co redirect), the link
  screen for accounts made with Gmail or email, plain Thai for every way a sign-in fails, the landing page and
  privacy terms open before sign-in, no app screen painted before the wall decides, and the back-office card that
  turns the wall off or on.
- **ai, vca, research**: the same wall on each origin's own session; an account without a Chula identity links
  one in place.
- **Never locked out while studying**: a saved session opens offline from the device, including one whose access
  token expired; inside LINE the wall offers the system browser.

## Production changes made before the merge (1 Nov)

- Auth: `mailer_autoconfirm` off and the Discord provider off after the security review found that Supabase links
  an identity by email when autoconfirm is on (a Discord account registered on someone's address could take the
  account over). Then the before-user-created hook on, manual linking on, and `https://ai.vetmock.com/**` and
  `https://vca.vetmock.com/**` added to the redirect URLs. All reversible.
- The migration, applied as one transaction with the switch off (recorded as `20261101170000 chula_wall`). A dry
  run first built 34 policies, the pre-request and both triggers and rolled back, leaving nothing behind. A probe,
  also rolled back, fired both triggers from a role without EXECUTE on them (as GoTrue's is): a Gmail address by
  email passed, a Chula address by email was refused, a Chula address by Google passed, an unverified Discord
  identity on an existing account was refused, a Google identity passed.
- After it: anonymous REST, a SECURITY DEFINER RPC, an allow-listed RPC and the AI's public counts answered as
  before; `chula_access_state` answers `{"enforce": false}`; PostgREST runs the pre-request (pg_stat_statements);
  `request.path` reads `/rpc/<name>`, the form the allow-list uses (checked with a temporary function, dropped).

## Checks

- Unit: 3,595 passed, 0 failed (6 todo, the retrieval evals marked weak). `chula-api-gate`, `chula`,
  `chula-subapps`, `use-auth-events` (an expired session's account survives auth-js answering no session; the test
  fails with the fix removed).
- SQL harness on the CI Postgres: `scripts/test-chula-wall-db.mjs` (who is let in, the switch, the hook, both
  triggers, the pre-request, the restrictive policies).
- Connected e2e, Chromium desktop and phone: 18 of 18 in `chula-wall.spec.js`, none skipped, plus the four other
  connected specs. The expired-token spec failed against a build with the fix removed.
- Sub-apps: ai 75/75, vca 353/353 plus `test:db` 14 checks, research 1,748/1,748 under both Asia/Bangkok and UTC;
  all three build.
- `lint:data` passed.
- Reviews: an adversarial security review and a correctness review of the whole change, then a third adversarial
  review of the fixes. Every finding was fixed or written into the limits. The third found no way for a non-member
  to reach data or paid API work; its fixes: signing out offline drops the token through the client's own storage
  (auth-js keeps it on a network failure), the offline account is read only under the client's own storage key, and
  a sign-in redirect is never preceded by the account already on the device. Each fix has a test that fails
  without it.
