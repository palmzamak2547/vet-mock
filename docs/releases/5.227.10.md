# 5.227.10: the first message to the assistant after an update is no longer refused

## What a person saw

On 15 Nov 2026, from 17:57, the first message sent to the assistant on a freshly started server was answered with "ระบบจำกัดการใช้งานขัดข้องชั่วคราว ลองใหม่อีกครั้งในไม่ช้า" and a 30-second wait. A second try went through. A visitor on a trial link met it at 18:02 and the owner at 18:04.

## Evidence

- Production logs of the last 23 hours hold the line `[rate-limit] shared limiter unavailable; request deferred` four times: 17:57, 18:02, 18:04 and 18:10, each on a different deployment, each on `/api/ai-chat`, each the first chat request of that deployment, all on `nodejs24.x` in `sin1`. None before 17:57.
- Six requests in a row at 18:10: the first answered 503 after 5.1 s, the next five 200 in 3.0 to 3.6 s.
- Production moved from Node 26 to Node 24 at 17:41 the same day (the pin that makes production run what the checks run on). No refusal of this kind is in the logs for the hours before it. That the move made the first call slower is likely and not proven.

## Cause

The limiter asks its store over the network and gives each call 1.8 s. The first call of a fresh instance also pays the name lookup and the TLS handshake. When that took longer than 1.8 s the limiter reported itself unavailable, and it fails closed because a chat costs money. Twelve deployments in one evening made nearly every first chat a cold one.

## The fix

`api/_lib/rate-limit.js`: the first store call of an instance is given 6 s; once one call has succeeded the limit is 1.8 s again, so a store that is really down still fails closed quickly. The first call logs how long it took (`[rate-limit] first store call of this instance took N ms`), so the next reading of the logs says what the real number is.

## Checks

- `tests/unit/rate-limit-cold-start.test.mjs`: a first call slower than the warm limit succeeds; the same slowness on a warm instance is refused.
- The existing limiter tests pass unchanged.

## Not verified

- How long the cold call takes on production: the new log line will say.
- Whether Node 24 is the reason the cold call became slower. If the log shows several seconds, opening the connection as the instance starts is the next step.
