# 5.160.0: Mochi reacts to each answer in practice

In practice with instant answers, the Mochi in the verdict stamp plays one reaction on the small
SVG rig the Motion Kit draws (`src/lib/mochi-live.js`) and ends on the exact frame the still image
shows. The rig is a lazy chunk (`mochi-live-*.js`) fetched at idle while the first question is
read. Reduced motion, a failed chunk or a stamp below the fold keep the still and its CSS greeting
as before.

- `MochiLive` plays the state `lib/mochi-reactions.js` picks over the still pose: correct, a hop at
  a run of 3, a high five at 5, a dance from 10, encourage on a miss. One reaction per revealed
  answer; a revisited question shows its verdict again without replaying anything.
- A run of right answers shows "ถูกติดกัน N ข้อ" from 3, counted from the set's own verdicts. Fill,
  match and writing questions neither break nor extend it; a wrong or skipped answer ends it. The
  chip pops on a spring and fades in under reduced motion.
- Android phones tick when the result shows: 14 ms for a right answer, two soft ticks for a wrong
  one, three for a run milestone. Only after a tap, never in a hidden tab, with a switch in
  "ตั้งค่า Mochi และการเคลื่อนไหว" that appears only where a vibration can be felt. iPhone has no
  vibration for websites.

## Frame cost of one reveal

Run with `node measure-reveal.mjs https://vetmock.com 5` under the machine's heavy lock (taken
20:02:11 +0700 after a 25 minute wait behind another job, released 20:06:36). Headed Chromium with
the GPU, a 390x844 touch phone viewport at device scale 2, CPU throttled 4x, the first right
answer of a 5-question practice set after 2 s of idle, frames sampled for 4.2 s starting just
before the click, median of 5 runs per arm. A is the rig chunk blocked (how the stamp behaved
before this release: the still and its CSS greeting); B is the rig playing. A frame is dropped
when its interval is over 25 ms (1.5 frames at 60 Hz); "click event" is the longest click or
pointerup event in the window.

- A: p95 frame interval 12.2 ms, max 145.4 ms, 8 dropped frames, long tasks 142 ms, click event
  184 ms, 564 frames in the window.
- B: p95 frame interval 13.1 ms, max 205.9 ms, 7 dropped frames, long tasks 275 ms, click event
  232 ms, 534 frames in the window.

So playing the rig costs 0.9 ms at the 95th percentile, 60 ms at the worst frame, 133 ms of long
tasks and 48 ms inside the click event, and no extra dropped frames, on this machine with this
throttle.

Limits of the numbers:

- Production moved from `assets/main-DT-qLWSa.js` (at the start of the run) to
  `assets/main-yfeBCqpQ.js` (at the end) as later merges were promoted. None of those commits
  touches the practice question view or the Mochi files (they change the notes layout, sign-in,
  library sources, shared links, a few lines of App.jsx and main.jsx, and add the Android shell),
  but the two arms did not both run on one bundle.
- The script's own `live` flag reads "still" in every run of both arms, because it is read 4.4 s
  after the click, when the reaction is over. That B plays and A does not was checked separately
  with the same flow (headless, same viewport and throttle): A's wrapper only ever read "still";
  B's went "playing", then "still" 1.4 s later.
- One machine, one display, five runs per arm; the maximum frame is the noisiest figure.
