# 5.163.3: Mochi's reaction no longer slows the answer tap

PR #72, merged as `66b2a79d` (Mochi and results lane).

- One rig is built in idle time after its chunk loads (`warmRig`) and reused; a reaction only moves it into place.
- MochiLive starts from an IntersectionObserver's first callback, after the verdict has painted (no forced reflow),
  and writes `data-mochi-live` on the element instead of a state update.

## Checks

- CI on `66b2a79d`: Build, Smoke e2e and VCA passed. Production deployment (vetmock) 2026-10-22 13:43 UTC.
- A/B on vetmock.com, 27 Oct, with the lane's own script (`measure-reveal.mjs`: headed Chromium with the GPU, 390x844,
  4x CPU throttle, median of 5; arm A blocks the rig's chunk, arm B lets it play). The laptop was on battery, so
  compare the arms, not the days.

| | click event | long tasks after the tap | p95 frame |
|---|---|---|---|
| 22 Oct, before: A / B | 184 / 232 ms | 142 / 275 ms | 12.2 / 13.1 ms |
| 27 Oct, after: A / B | 136 / 168 ms | 120 / 140 ms | 6.3 / 12.1 ms |

- What the rig adds to the tap went from 48 to 32 ms, and to long tasks from 133 to 20 ms. `data-mochi-live` read
  "still" in every run of both arms on both days, so in this scenario the reaction's animation itself did not play;
  arm B measures the rig's chunk and its idle build. The 100 ms target for the answer tap is not met in either arm
  at 4x CPU (AGENTS.md, performance budgets).
