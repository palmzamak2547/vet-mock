# 5.213.1: two fixes on the question card (a conflict chip that stayed, a way back that did not arrive)

## 1. The conflict chip no longer stays on the questions after a flagged one

Since 5.189.2 (2 Nov 2026), once a question carrying the "ข้อมูลขัดแย้ง" chip had been on screen,
the chip stayed on every question after it in the same set, and each further flagged question added
another one. The stale chip opened nothing when tapped. A student saw a red "MAJOR" warning on
questions that have no conflict at all. The bank has 22 flagged questions a student can meet (7
major, 15 minor); any set that contains one was affected from that question onwards.

### Cause

In `src/components/Question.jsx` the chip and the source line under it are children of the same
pane, and both were keyed by the question's id (`key={compoundId}`). React matches the children of
one parent by key. With two children sharing a key, the one that leaves when the question changes
is lost track of: its DOM node stays and nothing owns it. Both got that key in 5.189.2 (commit
`8d861ab9`), the source line so that a panel opened on one question would not stay open on the next.

### What changed

- The two keys differ: `flag:<id>` and `source:<id>`.
- `tests/unit/jsx-sibling-keys.test.mjs` reads every JSX file of the study app and the sub-apps and
  fails when two direct children of one parent carry the same key expression. Children made by
  `.map()` are their own list, the two branches of a conditional never show together, and two
  children that test one expression against different values (`view === 'a'` and `view === 'b'`)
  are left alone. It found no other case.
- `tests/e2e/flag-chip-own-question.spec.js` walks a whole topic forwards (and backwards when the
  draw put the flagged questions last) and asserts that the chip is on a question exactly when the
  bank flags that question. The chip's button carries `data-flag-chip` for it.

### Evidence

| | Before (main `ef993a0e`) | After (this branch) |
|---|---|---|
| The guard on `Question.jsx` | `Question.jsx:671 key={compoundId} is also the key of a sibling at line 431` | passes |
| A practice set of the Year-4 vaccine topic, 23 questions, 2 of them flagged | the unflagged question after "Top 5 Leptospira serogroups ในประเทศไทย" showed a chip, and tapping it opened nothing | 23 of 23 questions show the right number of chips (1 on the two flagged ones, 0 elsewhere) |

A second walk by a reviewer, on a build of main against a dev server of this branch: on main 10 of
23 questions carried a chip that was not theirs and the count grew to 9 chips on one card through
question-map jumps in a timed exam; on this branch none did, in practice, in a timed exam (forwards,
backwards and through the map), after submission, in a parked and resumed set and after a reload.
One difference a student could notice: a flagged question's note is closed again when they come back
to it (it used to stay open, because the stale chip was never replaced).

It was found by a hunt through the practice and exam flows on a production build of main (43
questions, 6 practice sets, 3 mock exams), which reproduced it four times.

## 2. The way back to a hidden table arrives

A question whose passage holds a table shows a floating "ดูตาราง" button once the table is off
screen. If the student had hidden the table, the button reopens it and scrolls back to it. On a slow
phone the table reopened and the page did not move: the button brought back a table nobody could see.

### Cause

The card asked for the passage by bumping a counter and scrolled on the next animation frame.
`SmartPassage` opened from an effect on that counter, one render later. When that render landed after
the scroll had started, the reopened table made the page taller above the reader; WebKit kept the
reader's place through the change and dropped the scroll that had just begun. It passed whenever the
render won the race, which is why main's own runs were green and this pull request's first run was
not: `tests/e2e/question-tables.spec.js` ("the way back to a table…") failed twice on webkit-mobile
with the table at viewport ratio 0, in a shard that this pull request had made busier.

### What changed

- `SmartPassage` opens on a new `openSignal` while rendering, so the table is on the page in the same
  commit as the tap and the one scroll measures where it really is.
- The scroll is instant when the student has motion turned down (the app's own setting or the
  device's): an explicit `behavior: 'smooth'` overrode the page's setting.
- `tests/unit/passage-opens-with-the-tap.test.mjs` pins the cause (no effect on `openSignal`, one
  scroll); the existing e2e covers what the student sees.

### Evidence

Traced with one script on a production build, 390x520, the table hidden and the page scrolled to its
end before the tap:

| | Before the tap | 250 ms after | Settled |
|---|---|---|---|
| main `ef993a0e`, WebKit | scrollY 346 of 346, no table | scrollY 611 of 611, table 168 px above the viewport | the same for good; the button still showing |
| main `ef993a0e`, Chromium | scrollY 346 of 346, no table | passage at the top of the viewport, table in view | the same; the button gone |

The final form of the fix (the passage opening in the same render as the tap) was not traced on a
build before it was pushed: the machine's dev server does not load in WebKit in time and the build
was still queued. This pull request's four-engine run of `tests/e2e/question-tables.spec.js` is its
proof, on webkit-mobile above all; it does not merge before that run is green.

## Known limits

- Nothing else about the chip changes here: its wording, which flags deserve a chip, and whether it
  shows before the answer are a separate change.
- The sibling-key guard compares key expressions as written. Two different expressions that produce
  the same value at run time are not caught; neither is a keyed element kept in a variable and placed
  beside a sibling with the same key. No such case exists today.
- Under any palette but the default one, a right answer takes the palette's accent (red under
  cherry). That is a separate fix, not in this release.
