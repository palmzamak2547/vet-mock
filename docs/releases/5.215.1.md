# 5.215.1: a document held for personal data is not listed or opened

## The gap

`text_status = 'pii_held'` marks a library file whose pages look like personal data (student or
national IDs, class lists, group rosters). Since migration `20261107140012` its page text was not
served, but the row and the file were: the two select policies on `library_docs` tested `status`
alone, and `library_doc_for_signing` returned the storage key of any public row, so
`/api/library-file` signed a link to the bytes. On 14 Nov 2026, before the review of the flagged
files began, 81 public rows were held and every one of them was listed on the shelf and opened for
any member. Nothing under `src/` or `api/` read `pii_held`.

## Every door, and what closes it

Read from the migrations and from production's live policies, functions and grants (no view reads
`library_docs`, and it is not in a realtime publication):

| Door | Closed by |
|---|---|
| The catalogue: the shelf, `findLibraryDoc`, the catalogue revision, the AI's title and slug reads (`api/_lib/ai/library.js`) | `library_docs anon read` and `library_docs member read` now skip a held row (this migration) |
| The file: `/api/library-file`, through `library_doc_for_signing` | no row for a held document, the same answer as a draft or an archived row (404) |
| Page text: `library_doc_pages` (browser, AI page fetch, video pipeline) | its policy, since `20261107140012` |
| Search: `library_search` (SECURITY DEFINER) | its own filter, since `20261107140012` |
| Topic links: `library_doc_links`, `library_related` (SECURITY INVOKER) | the link policy, and now the catalogue policies too |
| The `library-docs` storage bucket | its two read policies ask `exists (select 1 from library_docs ...)` as the caller, so the catalogue policies apply inside them. They are owned by the storage role, which the migration role cannot alter |
| Scripts (evidence build, video pipeline, MyCourseVille sync) | `SERVED` in `scripts/lib/library-read.mjs`, unchanged |

The admin (`is_admin()`) still lists a held row and gets its link, so a person can review the file
and clear the flag. The admin's row from `library_doc_for_signing` carries `held = true`, and
`/api/library-file` then signs it as restricted material: no cached link response, and the service
worker never keeps it as a public offline copy. `admin_overview` and `admin_extras` count every row
as before; scripts read through the Management API, which row security does not apply to.
Clearing `text_status` serves the document again at once. Nothing is deleted.

## Checks

- `scripts/test-library-held-db.mjs` (new, in CI's Annotation PostgreSQL job on postgres:17.6):
  applies the nine library and wall migrations in production's order to a Supabase-shaped
  database with six documents (public, restricted and archived, held and not), then walks each
  door as a member, a signed-in non-member, the admin and anon with the wall off. 13 checks, each
  door its own. On pglite: 13 passed. With this migration removed: 4 failed (catalogue member and
  anon, flag clearing, policy set). With only the signing rule removed: 3 failed.
- `tests/unit/library-pii-held-not-served.test.mjs`: the newest definition of both catalogue
  policies and of `library_doc_for_signing` carries the held rule; the old "library_docs public
  read" stays dropped; the harness applies the newest migration of every door (a later migration
  that redefines one fails it until the harness applies it); `/api/library-file` signs a held row
  `no-store` and `a: restricted`, an unheld public row as before. 11 passed; with the API rule
  removed, its test failed.
- `scripts/audit-library-pii.mjs` (read only, on production) now also checks every permissive
  reading policy on `library_docs` and `library_doc_for_signing`. Before the migration production
  answered `catalogue: false, signing: false`.
- An independent review looked for a way a member still reaches a held row. It found none in
  the database. What it raised and what was done is listed under "Not closed here".

## Not closed here

- A file a device opened before its flag was set stays in that device's offline copy
  (`vmx-lib-docs-v1`) and keeps opening from it. The database cannot reach it; pruning needs a
  service worker change.
- A file link minted before the migration lives at most 75 minutes (one window plus grace).
- Slide images already published to `slides.vetmock.com` are not pruned when their document is
  flagged later. The evidence build reads only served documents, and no held document is in the
  committed evidence index today.
- `library_doc_for_signing` does not ask `chula_access()`; `/api/library-file` applies the wall.
  Held rows are excluded either way.
