Two parked branches of 11 Nov 2026 folded into one release, numbered when its pull request opens:

## Part 1. The student profile (`claude/student-profile`)

What a student sees:

- One place to set the name and picture classmates see: the identity card on the profile hub edits in place, with a
  live preview row; the choice is written to `profiles.username` and `profiles.avatar_emoji` and shows at once in the
  header, the boards, groups and comments.
- A first-run step ("เพื่อนจะเห็นคุณแบบไหน"), once per account, on Home only, for a student who never chose a name:
  one screen, a switch for the board, a fixed save bar.
- The hub: the next paper from the timetable with the time left, a 28-day activity figure, earned badges and the
  nearest one with its progress, the student's own standing on the board, and an empty state with one next thing.
- The account page in four groups (identity, sign-in and security, your data, leaving) and one export that lists what
  it holds.
- The level is worked out from data that follows the account (answers and reviews in the synced record, quest points
  and a one-time carry of the old device counter in the account metadata), so it is the same on every device.
- The account page names the email once: a sign-in method that uses the account's own address names only the
  method (Quiet screens rule 1). Its "ลองอีกครั้ง" shows only when the list of passkeys failed to load, so a real
  account sees it only when there is something to retry.
- The hub's standing card keeps the rank line and the board button only: the groups entry is hidden everywhere for
  now, so the card no longer offers it.
- The board and groups say where the student stands: hidden by choice, ranked N of M, or not in the first 200.
- The wall's sentence about Google now says the app uses only the name and email; the board and group screens are
  in Thai; the account page has one name ("บัญชีและข้อมูล") everywhere.

Design, as the lane recorded it: the hub is two columns from 1024 px; motion is transform and opacity only (editor
entrance, picture settle, figure bars rising with a geometric stagger, the save line), nothing under reduced motion.

### Where the profile keeps things, and who can see each

| What | Where | Who can read it |

| Board choice | auth `user_metadata.show_on_leaderboard` | The student (their session) and the definer leaderboard RPCs, which read it to leave the student off the board; no other member |
| First-run done | `user_metadata.identity_intro_done`, and `localStorage` `vmx-identity-intro:<uid>` | The student only |

| Level carry | `user_metadata.xp_quests`, `user_metadata.xp_carry[<device id>]` | The student only (metadata rides in the student's own token) |
| Device bookkeeping | `localStorage` `vmx-xp`, `vmx-xp-counter-owner`, `vmx-xp-pending:<uid>`, `vmx-xp-carried:<uid>`, `vmx-device-id` | That browser only |

### Database steps, final

Written 15 Nov 2026 as four migration files, each with a header that says what it does, what it never touches,
the count query to run first (counts only), which live client call meets it, and how to take it back. They replace
the list the lane wrote down; "Needs a migration" below is kept as the record of where they came from. None of them
is applied by the pull request that adds them; a person applies them by hand, in this order, after a second reader.
`scripts/test-profile-names-db.mjs` walks all four on CI's Postgres (job "Annotation PostgreSQL").

| # | File | What it does | Count first |
|---|---|---|---|
| 1 | `supabase/migrations/20261115140000_profile_name_rules.sql` | Functions in `private` (the recogniser, the rules for a new name, the folded form, the neutral handle, one-account change and undo, two passes) and the undo table. Changes no row. | `select count(*) as undo_rows from private.profile_name_undo;` (0) |
| 2 | `supabase/migrations/20261115140100_profile_neutral_handles_apply.sql` | Gives every leaking name a neutral handle; prints only how many accounts it changed. | the query by reason in its header (about 12 expected) |
| 3 | `supabase/migrations/20261115140200_profile_identity_guard.sql` | The name and picture rules on every rename from the app (23514, `public name refused: <reason>`), the neutral handle for a new row that would leak, `profiles_update_own` with `WITH CHECK`. Changes no row. | names and pictures outside the rules, counted; they stay |
| 4 | `supabase/migrations/20261115140300_profiles_username_folded_unique.sql` | Unique index on the folded name. Alone, outside a transaction (`concurrently`). | collision groups; if not 0, `select private.neutralise_folded_collisions();` first |

The count query for file 2, as in its header:

```sql
select count(*) filter (where reason = 'student number') as student_number,
       count(*) filter (where reason = 'email') as email,
       count(*) filter (where reason = 'address') as address,
       count(*) as accounts
from (select private.public_name_leak(p.username, u.email) as reason
      from public.profiles p left join auth.users u on u.id = p.id) s
where reason is not null;
```

What was decided for the 12 names:

- The rule (`private.public_name_leak`) is the app's own: what `shownName` draws as an id (7 or more digits after
  NFKC, Thai digits counted, invisible characters removed, one separator between digits joined) or a bare run of 5
  or more digits (`isAutoName`) is a student number; the name equal to the account's own mail local part (trimmed,
  any case), or to that part as `handle_new_user` stores it, is the email; an `@`, `http:` or `www.` is an address.
  Two additions to the app's rule: Thai marks are dropped before counting digits, so a mark cannot hide a run, and
  the stored form of the local part (`somchai.j` stored as `somchaij`) counts. A name with digits that is none of
  these ("ploy55555", "vet86 2567") is left.
- The neutral handle is `user_` and six letters from a to f: the state the app already gives a name nobody chose
  (`isAutoName`), so Home greets "นิสิต", the identity card asks for a name, and other members see the handle. It
  has no digit, so it never reads as a number, and it says nothing about the person.
- The step also takes `identity_intro_done` out of those accounts' metadata, so the first-run step asks for a name
  again. It shows once the token carries the new metadata (next refresh or sign-in). A device where the student
  already closed the step keeps its own flag (`vmx-identity-intro:<id>`) and does not show it again; the greeting
  and the identity card still ask there.
- Old name, new handle and the old first-run flag go to `private.profile_name_undo`: no grant to any API role, row
  security on with no policy, read by the admin in the SQL editor. `private.undo_neutral_handle(<id>)` takes one
  account back, unless its student has chosen a name since. A deleted account takes its undo rows with it.
- Not changed: a question already shared in a group keeps the `author_name` written when it was shared (counted in
  file 2's header), and the roughly 300 names made from the Google name stay until their students choose (the app
  already treats them as not chosen).

What the corrections the security review asked for became: the index is its own file outside a transaction and
uses the compact form of `compactName`; each refusal has its own message under 23514, and only the length rule names
"length"; the handle has no digit run and `identity-gate.js` already knows it, so no code change is needed; the
digit rule drops Thai marks and refuses a mark on a digit; every database refusal is also one the app makes (the test
holds them together); `handle_new_user` and `ensure_profile` are not rewritten, since neither is defined in this
repository: a BEFORE INSERT trigger gives the handle to a new row whose name would leak, is made from the Google name
or is taken in the folded form. Left out on purpose: the `show_on_boards` column, which does nothing until the app
reads and writes it.

What the code in this release does while none of it is applied:

- No save fails and no field is dropped: `saveIdentity` writes only `username` and `avatar_emoji` (columns members
  may already update) and the metadata keys above.
- The name and picture rules exist only in the browser (`checkPublicName`, the picture set), and the app draws a
  leaking value as "นิสิต" and the paw (`shownName`, `shownPicture`), but the raw value stays readable to members
  through the API until file 2 and file 3 are applied.

## Needs a migration (from the profile lane, not applied)

Superseded by "Database steps, final" above; kept as the record the final files were written from.

What the database accepts today for a name: `profiles.username text unique not null`,
`profiles_username_length_check` 2 to 30 characters (NOT VALID, so enforced on every new write), any
character (Thai included). `avatar_emoji` up to 32 characters. Members may update only `username`
and `avatar_emoji` of their own row (`profiles_update_own`, USING and WITH CHECK `auth.uid() = id`).
Everything else in the name rules (reserved words, emails, student numbers, the picture set,
case-insensitive uniqueness) is client-side only until this lands:

```sql
-- 1. Name and picture rules at the database boundary.
create or replace function private.public_name_problem(p_name text, p_email text)
returns text language sql immutable as $$
  select case
    when p_name is null then 'empty'
    when p_name <> btrim(regexp_replace(normalize(p_name, nfc), '\s+', ' ', 'g')) then 'not normalised'
    when char_length(p_name) not between 3 and 24 then 'length'
    when p_name !~ '^[ก-๛A-Za-z0-9_ .-]+$' then 'characters'
    when p_name ~ '@' or p_name ~* '(www\.|https?:|\.(com|net|org)$)' then 'address'
    when translate(regexp_replace(p_name, '[ ._-]', '', 'g'), '๐๑๒๓๔๕๖๗๘๙', '0123456789') ~ '[0-9]{5,}' then 'digits'
    when lower(p_name) = lower(split_part(coalesce(p_email, ''), '@', 1)) then 'email'
    when lower(regexp_replace(p_name, '[\s._-]', '', 'g')) ~ '(admin|staff|vetmock|moderator|support|system|official|owner|root|แอดมิน|ทีมงาน|ผู้ดูแล|เจ้าหน้าที่|อาจารย์)'
      or lower(regexp_replace(p_name, '[\s._-]', '', 'g')) in ('mod','dev','team','null','undefined') then 'reserved'
    else null end
$$;

create or replace function private.guard_public_identity()
returns trigger language plpgsql security definer set search_path = public, pg_temp as $$
declare problem text;
begin
  -- The auth trigger and the service role keep their own paths.
  if coalesce(current_setting('request.jwt.claims', true), '') = ''
     or (current_setting('request.jwt.claims', true))::jsonb->>'role' = 'service_role' then
    return new;
  end if;
  if new.username is distinct from old.username then
    problem := private.public_name_problem(new.username, (select email from auth.users where id = new.id));
    if problem is not null then
      raise exception 'public name refused: %', problem using errcode = '23514';
    end if;
  end if;
  if new.avatar_emoji is distinct from old.avatar_emoji and new.avatar_emoji is not null
     and new.avatar_emoji <> all (array['🐾','🐶','🐱','🐰','🐹','🐴','🐮','🐷','🐑','🐐','🐔','🦆','🐢','🐠','🦜','🐍']) then
    raise exception 'picture refused' using errcode = '23514';
  end if;
  return new;
end $$;

drop trigger if exists tr_guard_public_identity on public.profiles;
create trigger tr_guard_public_identity before update of username, avatar_emoji on public.profiles
  for each row execute function private.guard_public_identity();

-- 2. Case-insensitive uniqueness. First list collisions and resolve them by hand:
--    select lower(username), array_agg(username) from public.profiles group by 1 having count(*) > 1;
create unique index concurrently if not exists profiles_username_lower_key on public.profiles (lower(username));

-- 3. Stop making public names from the Google name or the email local part (handle_new_user):
--    replace its base_username with a neutral handle, e.g.
--      base_username := 'นิสิต_' || substring(replace(NEW.id::text, '-', '') from 1 for 6);
--    keeping the collision loop and the EXCEPTION block as they are.
```

**Corrections the security review found in the SQL above (fd9bec89), to make when the database
step is written; not built in this branch:**
- `create unique index concurrently` cannot run inside a migration transaction: give it a migration
  of its own outside a transaction, or drop `concurrently`.
- Index the compact NFKC form, not `lower(username)`: the same folding as `compactName` in
  `src/lib/public-identity.js` (NFKC, sara am recomposed, case, separators, I/l/1 and O/0). List
  and clear the collisions in that form first.
- Every refusal raises 23514, which the client read as a length error. The client now says "length"
  only when the message names the length check. Better still, give each refusal its own message
  (`public name refused: digits`) and keep the 23514 code.
- The proposed handle `'นิสิต_' || 6 hex` is not recognised as auto-made by `isAutoName`, and it
  holds five digits in a row about 19 percent of the time. Use a handle with no digit runs, such as
  `'นิสิต_' || <6 letters from a-p>`, and add its pattern to `identity-gate.js`.
- The `public_name_problem` digit rule has the same tone-mark gap the client had (`643่12345`): strip
  the Thai marks (U+0E31, U+0E34 to U+0E3A, U+0E47 to U+0E4E) before counting digits, and refuse a
  mark directly after a digit. Normalise with NFKC, not NFC.
- No existing row is fixed by the trigger, which only runs on update. About 300 rows hold an
  auto-made or Google-derived name. They need a one-time pass (the student is asked through the
  first-run step, which already treats those names as auto-made).
- `show_on_boards`: do not grant SELECT on it to members. The leaderboard RPCs read it as
  definer, and it is kept in sync with the metadata flag while older clients still write only the
  metadata. Drop the `grant select (..., show_on_boards)` line below.

The policy stays as it is, written out so its `WITH CHECK` is explicit in the same migration:

```sql
drop policy if exists "profiles_update_own" on public.profiles;
create policy "profiles_update_own" on public.profiles
  for update to authenticated
  using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);
```

### Comments honouring the board choice
Comments join `profiles(username, avatar_emoji)` and cannot read another member's auth metadata.
To let a student hide their name there, move the flag into `profiles`:

```sql
alter table public.profiles add column show_on_boards boolean not null default true;
update public.profiles p set show_on_boards = coalesce((u.raw_user_meta_data->>'show_on_leaderboard')::boolean, true)
  from auth.users u where u.id = p.id;
revoke update on table public.profiles from anon, authenticated;
grant update (username, avatar_emoji, show_on_boards) on table public.profiles to authenticated;
-- no SELECT grant on show_on_boards: the RPCs read it as definer (review, item 7)
-- profiles_update_own above (USING and WITH CHECK auth.uid() = id) covers the new column.
```
then the leaderboard RPCs read `p.show_on_boards`, the client writes it in `saveIdentity`, and the
comment list shows "นิสิต" for a row whose author has it off. The `"chula members only"` restrictive
policy already covers `profiles`.

### The level
No migration: the carried number lives in auth metadata, which the student already writes. A
`user_data.xp` column would only matter if quest history itself should be restorable.

#### What changed (English)

The owner asked for a much better profile system (11 Nov 2026). An audit of main ef993a0e found the
picture a student picked was saved and shown nowhere, the edit form could publish the student number,
year/cohort/bio were collected and read by nothing, the hub claimed the level was kept in the account,
and the board choice was one buried checkbox. This change fixes those and rebuilds the hub and the
account page. No database migration, no row-policy change, no new table or column, no sign-in change.

##### Defects
1. **One write path.** `saveIdentity()` (`src/lib/supabase.js`) writes `profiles.username` and
   `profiles.avatar_emoji` first (only those two columns, never the key; own row via
   `profiles_update_own`), then mirrors to auth metadata (`show_on_leaderboard`,
   `identity_intro_done`). The hub, the first-run step and the account page all use it through
   `IdentityEditor.jsx`; App updates its profile state from the returned row, so the header, hub,
   board and comments show the choice with no reload. `updateUsername` is gone.
2. **Never the email local part.** The editor starts empty for an auto-made name, the header shows
   "นิสิต" while the profile loads, signup no longer proposes a name from the email, and
   `validateUsername` refuses five digits in a row. An auto-made name (`user`, `user_N`,
   `user_<hex>`, the stand-in, a digit run, the email local part) is said for what it is.
3. **First-run step** (`IdentityStep.jsx`, gate `src/lib/identity-gate.js`): once per account, on
   Home only, never with a set waiting to resume, never over the wall's welcome or the tour, only
   for a student who never chose a name. Skipping counts (device flag plus `identity_intro_done`).
4. **One year.** The hub reads the app's year (`vmx-selected-year`, App's `selectedYear`) and
   derives the cohort from `SEMESTER.cohortNote`. Year, cohort and bio are no longer asked for;
   values saved earlier stay in metadata and in the export.
5. **Privacy explained.** The editor lists every surface and whether the board choice hides the
   student there. Comments and a group's member list read `profiles` directly and ignore the flag:
   the UI says "แสดงเสมอ เลือกซ่อนไม่ได้". The leaderboard and group board show the student's own
   line (`BoardPresenceNotice.jsx`): hidden by choice, ranked N of M, or not on the board yet.
6. **True statements, one level.** The hub claims nothing about storage and carries no caveat.
   The level is one function of data that follows the account (`shownXp` in `lib/xp.js`, read by
   the hub and the header chip): answers in the synced history (5 right, 2 wrong) and reviews on
   synced SR cards (3 each), plus metadata `xp_quests` (quest points, the one award no synced record
   holds; the daily question and reading grant no XP) and `xp_carry[<device>]` (the old counter's
   lead, recorded once per device). After the security review (fd9bec89):
   - no carry until the sync store has finished this account's first pull (`xpReady`, phase
     synced or pending), since before that the history is empty and every answer would count twice;
   - the old counter is carried only by the account this phone's data store belonged to when this
     release first loaded (`vmx-xp-counter-owner`, read from `vmx-user-sync-owner-v1` once, in
     `xp.js`, before anyone can sign in), so a second student on a shared phone never inherits it,
     in either order (third read). A phone with no recorded owner (a guest's phone, a fresh browser)
     carries nobody's counter: a student there gets the account's own calculation, the same on
     every device. If that is below the old counter they see the lower level once, after the first
     sync, and from then on the same level everywhere. Quest points are kept per account
     (`vmx-xp-pending:<uid>`);
   - until sync is ready the header chip shows the higher of the account's number and the counter
     where the counter is theirs, and never less than the frame before, so a load does not flash
     the level away and back;
   - the carry is set per device, never added, and quest points flush under a Web Lock, so two tabs
     cannot double it (a browser without Web Locks can still double a flush of quest points);
   - until the carry lands, the device in use shows its own counter where it is higher, so nobody's
     level drops; afterwards every device shows the same number.
   Tests: `tests/unit/student-identity-review.test.mjs` (early effect, second account, two tabs, one
   function).
7. **No algorithm names.** The review row read "เลือก SM-2 หรือ FSRS ได้ในหน้านี้"; it now says what
   the student gets: "ข้อที่ผิดกลับมาให้ทบทวน แอปเลือกวันให้เอง". Test: "the review row says what the
   student gets, no algorithm names".
8. **One streak for the tile and the trophies.** The prototype showed a streak tile of 4 beside
   "2 จาก 7 วันต่อเนื่อง": the tile reads the saved streak (it knows a freeze), the trophy read the
   longest run in history. `badgeMetrics` now takes `currentStreak` and counts the longer of the two,
   and the hub hands it the tile's own number, so the tile and "next trophy" cannot disagree (a
   streak-7 trophy is earned when the tile reads 7). The phase summary still counts history alone.
   Test: "the streak tile and the streak trophies read one number".

### Instructor portraits on the faculty screen and in a profile

Asked for: complete the instructor profiles with each lecturer's portrait. The portraits are the
institutions' official staff portraits, shown to signed-in members, with permission recorded by the
owner on 11 Nov 2026.

#### What changed

- A profile in `src/data/instructors-directory.js` may carry `photo: { w, h, v }`: pixel size (a
  square, 320 px or the source's own size when smaller) and the first 8 hex of the file's SHA-256.
  Nothing else about the picture is in the app.
- `scripts/instructor-portraits.mjs` holds one line per portrait: slug, size, hash, the staff page,
  the image's address on that page and the date fetched. `--write` applies the list to the
  directory; `scripts/generate-instructor-directory.mjs` applies it too, so a regeneration keeps it.
  `npm run lint:instructor-portraits` (in `lint:data`) checks the `photo` shape, that every `photo`
  has a line and every line a `photo`, and that each source is a department staff page of
  vet.chula.ac.th or the CULAC staff page.
- `InstructorPortrait.jsx` draws a 48 px box on each faculty card and a 72 px box in the profile:
  the portrait (`loading="lazy"`, `decoding="async"`, alt text the person's name) or the initials of
  the name in the app's own colours. The box is the same size either way, so nothing moves when a
  picture arrives. Nothing else on those screens changed.

#### Sources and the pairing rule

- The twelve department pages on vet.chula.ac.th (the addresses `npm run audit:instructors` reads,
  English and Thai, 24 pages) and https://culac.chula.ac.th/about/staff. GETs only, one at a time
  with a pause between requests.
- A portrait was taken only when it is the picture of a staff card (`grid-item list-profile`, its
  `grid-image` box) whose name, titles trimmed, equals one profile's `nameEn`, `nameTh` or an alias
  exactly. The English and Thai pages print the same cards in the same order (all 201 card
  positions carry the same image and email on both), so a card position is one person: a Thai name
  that matches makes the card that person's even when the English spelling differs.
- Rejected: an image used by cards of different people, an address that reads as a logo or a
  placeholder, anything under 120 px, a card naming two profiles, a person with two different
  pictures. Then every accepted portrait was looked at on a contact sheet.
- The picture: one square from the centre-top of the source, 320 px WebP (smaller sources kept at
  their own size, never enlarged), no other change. 6.8 to 16 KB each.
